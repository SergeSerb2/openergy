# Linux release-readiness audit — 2026-10-21

Scope: `crates/platform-linux` and `tools/linux-dev`. Base: `06b6128`.
All input and selection operations ran inside an isolated ARM64 Debian Bookworm
Docker container with Xvfb at `DISPLAY=:99`. Rust was
`1.99.1 (58cf8f9c3 2026-10-13)`. No installed application, host desktop,
host clipboard, native permission, live configuration or unowned process was
used. No daemon or TCP listener was started; neither assigned port range was
needed. No unit tests or mocks were added. The probes use the public Backend /
ClipboardBackend interface, a real X server, and real external X11 clients.

## Reproduced failures and fixes

The original probe suite passed before this audit. New probes then exposed the
following failures through the real X server. Diagnostic modes are supported by
`tools/linux-dev/linux-dev.sh run MODE`.

| Mode | Observed failure before its fix | Resulting behavior |
| --- | --- | --- |
| `recovery` | `Refused pointer grab leaked the capture keyboard grab` | A refused pointer grab checks/flushes rollback of the keyboard and pointer grabs. Cursor setup failures use the same cleanup path. Capture stop still releases the keyboard. |
| `inject-recovery` | `Sink released a Shift held by another X client` | Key ownership is recorded separately from source-button identity. Repeat and release affect only keys owned by the sink. Shared remote modifiers still remain held until their last user releases them. |
| `inject-recovery` | `Sink released a mouse button held by another X client` | XI2 button state includes extra buttons. Duplicate downs and unowned ups do not release a local button. Release-all preserves already held local input. |
| `keymap-recovery` | `Unicode release overwrote a newer X client keymap` | Unicode cleanup compares the current server mapping with the installed fallback before restoring it. A newer external mapping survives. Normal fallback restoration still passes. |
| `lock-recovery` | `Lock-state sync released a local lock key instead of refusing injection` | Lock synchronization refuses a toggle while that native lock key is held. The local key remains down and the injection returns an error. |
| `clipboard-recovery` | `X11 selection transfer timed out` after a small read followed by a larger read of the same xclip owner | Each conversion has a separate disposable requestor window. Oversized INCR data is drained without retention, within the fixed ten-second/256 MiB limits. A later read from the same xclip owner succeeds. |
| `clipboard-stamp` | `Own selection notification changed the stamp after write returned` | The synchronous write advances its stamp once. Its queued XFixes notification does not advance the stamp again. |

Additional resource fixes from inspection:

- DestroyNotify immediately removes outgoing INCR transfers. Completion and
  expiry remove this client's property/destroy subscriptions on the requestor.
  There are at most 16 transfers with a combined 256 MiB byte budget. A second
  request cannot replace an active transfer on the same window/property.
- Incoming property/type/format validation also supports ATOM/32 INCR TARGETS.
  Empty INCR size headers remain accepted for xclip 0.13 compatibility. A
  deadline is checked before consuming each event, so unrelated events cannot
  extend the deadline indefinitely.
- Wake sockets are nonblocking. Socket error/hangup stops the wait loop rather
  than spinning. The display monitor exits on a failed X connection. These
  failure branches were reviewed; X-server death was not separately exercised.
- The helper verifies Xvfb startup, uses `-noreset`, limits Cargo to two jobs at
  niceness 15, bounds probe execution, and uses locked builds. Cleanup selects a
  worktree label rather than all containers with the former shared prefix.
  Build/check scope now selects only the Linux platform crate.

The INCR framing checks follow [ICCCM selection transfer conventions](https://www.x.org/releases/current/doc/xorg-docs/icccm/icccm.pdf).
The compatibility exception for an empty advisory count is present in
[xclip 0.13's owner implementation](https://github.com/astrand/xclip/blob/0.13/xclib.c).
No third-party implementation code was copied.

## Limits and integration handoff

This is native backend evidence on Xvfb, not physical Linux desktop acceptance.
Physical input devices, window managers, applications that reject X SendEvent,
non-US/dead-key/AltGr layout matrices, real display hotplug, and X-server death
remain unverified. RandR worker teardown was exercised, not real hotplug.
Wayland remains unsupported. No performance, packaged distribution, or broad
compatibility claim follows from these checks.

The helper image was already present and was reused; a fresh Docker image build
was not needed or verified. The Dockerfile was unchanged. Native prerequisites
and optional extensions are documented in `tools/linux-dev/README.md`.

Parent integration still needs the full daemon/external E2E suite and the
workspace toolchain/MSRV gate. Neither daemon behavior nor root build metadata
was changed here. No cross-scope implementation defect was confirmed.

## Shared clipboard contract follow-up

This follow-up depends on platform API commit `ffdd07a`, already present in the
parent integration. The Linux reader previously returned `Ok(formats = [])`
when an existing owner offered only unsupported formats or refused its payload
conversion. With the session now forwarding real clears, that result could erase
a peer's clipboard. The new external Xvfb probe reproduced the unsupported-only
failure before the source fix:

```text
clipboard contract: stable ownerless selection is a real clear
clipboard contract: external text and zero-byte UTF-8 remain readable
x11_probe: Unsupported-only selection was not ClipboardUnavailable
```

The reader now returns `ClipboardUnavailable` for unsupported-only owners,
refused conversions, missing promised properties and changing snapshots. Owner
identity and the per-selection XFixes stamp are checked across the complete read.
Notifications queued before the initial owner query completes are processed
before taking the baseline stamp. A stable ownerless selection and the backend's
own explicit empty write still return a successful empty payload. Zero-byte
UTF-8 and HTML retain their formats and empty bytes, including with a zero-byte
read limit. Invalid data and oversized data retain their existing error types.

A full cherry-pick of the shared API commit conflicted in unrelated virtual
backend changes and was aborted. Only its `crates/platform/src/lib.rs` contract
patch was applied locally for validation, then removed. No shared platform files
are part of the Linux follow-up commit. On this isolated branch, reproduce the
checks with the API contract present; the parent already has it:

```sh
# Test-only API patch, applied from an otherwise clean checkout:
git show ffdd07a --format= -- crates/platform/src/lib.rs | git apply
tools/linux-dev/linux-dev.sh run clipboard
tools/linux-dev/linux-dev.sh run clipboard-recovery
tools/linux-dev/linux-dev.sh run check
nice -n 15 cargo fmt -p openergy-platform-linux -- --check
git diff --check
# Remove only the temporary API patch after validation:
git restore --worktree -- crates/platform/src/lib.rs
```

All checks passed. The native release build and all-target Clippy completed with
zero warnings. `clipboard` also passed the existing 10,498,508-byte INCR image
transfers, independent pixel comparison, PRIMARY isolation, explicit empty write
and malformed-image checks. The new real-client acceptance output was:

Independent xclip processes supplied normal, zero-byte and unsupported-only
