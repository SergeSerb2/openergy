# Wayland backend design

Design only. Written 2026-11-09 against Openergy commit `19e93a565704851fb265deaaf682c5b76c003de5`.
No Wayland support is implemented or verified by this document. External links describe the upstream interfaces inspected on that date, not a guarantee about a distribution package.

## Decision

Add an explicit `wayland` backend inside `crates/platform-linux`. Keep X11 as a separate backend. Use **InputCapture + an EI receiver for the server**, and **RemoteDesktop + an EI sender for the client**. Here, server/client mean Openergy roles. Both are clients of the compositor's EIS service. Openergy does not implement an EIS server. The compositor owns input policy; EI transports the authorized events. [libei architecture](https://libinput.pages.freedesktop.org/libei/api/index.html)

Ship client injection before server capture. Server support requires an explicit change to the shared capture contract and session integration. It cannot be a drop-in implementation of the current `InputSource`. Do not emulate global capture with an invisible fullscreen window, root access to input devices, or XWayland. Do not advertise full feature parity on any compositor until the real acceptance flows below pass.

Use runtime capability discovery, not desktop-name checks, to choose transports. The initial supported product path is the portal path on Mutter/GNOME and KWin/Plasma. An optional, explicit wlroots injection/clipboard path follows later. Missing InputCapture means **no server role**, even if virtual input and screen capture work.

The shared `key` is a `u16`: this design preserves the existing BMP/special-key encoding and surrogate rejection. It does not add supplementary-plane Unicode to the wire contract. A Wayland project is not an opportunity to claim that `sync_language` changes desktop layouts everywhere.

## 2. Wayland facts that constrain the mapping

**Capture is an activation session.** InputCapture provides output zones, boundary barriers, activation IDs and relative input through EI. Enable arms a session; only the compositor activates it. Release ends an activation and can suggest a return position. The compositor can deactivate/disable capture. ZonesChanged invalidates the old zone setup. There is no application request for an immediate arbitrary grab or event-by-event native replay. [InputCapture contract](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.InputCapture.html)

**Version negotiation matters.** InputCapture v1 uses the original CreateSession flow, which also starts the session. V2 adds CreateSession2/Start, persistence and pre-Start clipboard negotiation. RemoteDesktop v2 includes persistence, ConnectToEIS and clipboard integration. Restore tokens are single-use: retain the replacement after a successful start. Neither a stored token nor a frontend interface version proves that the selected desktop backend will restore a grant without a dialog. [InputCapture XML](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.portal.InputCapture.xml), [RemoteDesktop contract](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html)

**Core Wayland is surface-scoped.** Normal pointer/keyboard input follows focus, pointer positions are surface-local, and setting a cursor concerns a client's focused surface. Selection writes need a valid input serial and clipboard offers follow focus. This does not give a background daemon global observation, a global pointer query, global cursor hiding or unrestricted clipboard access. Relative-pointer and pointer constraints do not remove that scope. [Core protocol](https://wayland.freedesktop.org/docs/html/apa.html)

Even the newer `wp_pointer_warp_v1` requests a surface-local position with an enter serial; it is not XWarpPointer for the desktop. [Upstream pointer-warp XML](https://github.com/wayland-mirror/wayland-protocols/blob/main/staging/pointer-warp/pointer-warp-v1.xml)

**Upstream availability differs.** GNOME's source includes InputCapture, RemoteDesktop and Clipboard implementations, including InputCapture clipboard/persistence state. KDE advertises all three and has separate capture/clipboard code. This establishes implementation paths, not a verified minimum desktop release. In contrast, upstream xdg-desktop-portal-wlr lists Screenshot and ScreenCast, not those input portals. Distribution patches or other portal backends can differ. [GNOME sources](https://github.com/GNOME/xdg-desktop-portal-gnome/blob/main/src/meson.build), [GNOME capture](https://github.com/GNOME/xdg-desktop-portal-gnome/blob/main/src/inputcapture.c), [KDE declaration](https://github.com/KDE/xdg-desktop-portal-kde/blob/master/data/kde.portal), [KDE capture](https://github.com/KDE/xdg-desktop-portal-kde/blob/master/src/inputcapture.cpp), [KDE clipboard](https://github.com/KDE/xdg-desktop-portal-kde/blob/master/src/clipboard.cpp), [wlr supported portals](https://github.com/emersion/xdg-desktop-portal-wlr#readme)

In the following tables, **partial** means the design needs an explicit reduced contract. **GAP** means the stated trait behavior has no supported equivalent in the selected path. A listed mechanism is not a claim that Openergy already supports it.

## 3. Requirement mapping by compositor family

`IC` means InputCapture; `RD` means RemoteDesktop. For Mutter and KWin, each portal cell requires the running backend to support the method, grant the requested devices, and expose usable EI capabilities. For wlroots, extension cells require advertised globals and successful use; the library family alone grants nothing.

### Capture, injection and keys

| Platform behavior | Mutter / GNOME | KWin / Plasma | wlroots family |
| --- | --- | --- | --- |
| `InputSource::start/stop`: observe all input while local | **GAP** in IC: no passive global input stream while inactive. Start prepares/arms a session; stop disables delivery. The broker closes the session on authorization reset or shutdown. | Same IC limit. | **GAP** in baseline wlr portal stack. Ordinary seat events are focused, not global. A different installed IC backend could qualify through discovery. |
| `set_cursor_captured(true)` / immediate grab | **Partial:** acknowledge an existing compositor activation; cannot cause activation on demand. | Same. | **GAP** without IC or a new compositor-specific capture integration. Virtual input is not capture. |
| `Swallow` | During active IC, the compositor diverts input from local apps. Keep capture active. Cannot swallow an earlier local event. | Same. | **GAP** in baseline path. |
| `PassToOs` / `PassOnce` | Release can end capture for future input. **GAP** for replaying the current event and for one local release while capture stays active. | Same. | **GAP** for the full callback contract. Input inhibitor is not a portable replay API. |
| Relative motion, buttons and wheel capture | Active EI receiver device capabilities; carry fractional motion into integer events, normalize button IDs and wheel units. | Same. | **GAP** without IC; a virtual-pointer sender cannot observe physical motion. |
| `warp_cursor(x,y)` | **Partial:** suggest position at IC Release. No guarantee or general inactive warp. | Same. | Virtual pointer can send absolute motion when permitted; this is injection, not a background query or capture release guarantee. |

Convert KeyID to target keycode/level, preserving source-button identity. | Same. | `zwp_virtual_keyboard_v1` accepts a client keymap and key/modifier requests. It does not query a global physical keyboard. |

| Missing-layout Unicode fallback | No X11 spare-key remap. Optional EI text/keysym capability can provide an alternative; otherwise fail that injection. | Same capability gate, not a blanket KDE exception. | A private virtual-keyboard keymap can include missing symbols; release owned keys before replacing it. Validate behavior against the real compositor. |
| Caps/Num/Scroll lock synchronization | Use observed EI modifier state; synthesize owned toggle pairs only with known state and synchronization. Unknown state is a **GAP** for guaranteed synchronization. | Same. | Virtual-keyboard modifiers control its own logical state. Global lock/LED parity with physical devices is **not guaranteed**. |
| `release_all`, `permissions_changed` | Track and release only owned keys/buttons, then end emulation. Permission/device loss cancels pending input; never reuse old device handles. | Same. | Release owned virtual keys/buttons before destroying device objects. No synthetic release of another device's input. |
| `set_cursor_visible` | **GAP** for arbitrary global hide/show. IC's compositor-controlled cursor behavior covers active server capture only after acceptance. | Same. | Also **GAP** for global hide/show through ordinary client APIs. |

EI keycodes use Linux input codes; XKB lookup needs the conventional evdev-to-XKB offset, not the X11 source button value. The keymap belongs to a device and is constant for its lifetime. Modifier feedback and a connection sync are available, but unrelated physical activity can still race a sender. [EI keyboard protocol](https://libinput.pages.freedesktop.org/libei/interfaces/ei_keyboard/index.html)

EI sender events need frames and valid resumed devices. Region coordinates belong to the EIS coordinate space, which can differ from physical pixels. Preserve a device/region transform rather than assuming `wl_output` geometry equals EI geometry. [EI device protocol](https://libinput.pages.freedesktop.org/libei/interfaces/ei_device/index.html), [sender API](https://libinput.pages.freedesktop.org/libei/api/group__libei-sender.html)

Current EI also defines `ei_text.keysym` with down/up and `ei_text.utf8`. Thus “Wayland/libei cannot inject Unicode” would be too broad. Text is optional, negotiated separately, and UTF-8 commit need not produce keyboard events. Choose **keysym down/up** as the optional missing-symbol fallback because it fits the existing event ledger better. Do not silently replace shortcuts or held keys with text commits, clipboard paste, Ctrl+Shift+U sequences, or an input-method takeover. Without a working text capability and unmapped-key acceptance, report `injection_failed`. [EI text protocol](https://libinput.pages.freedesktop.org/libei/interfaces/ei_text/index.html)

The optional wlroots adapter uses protocol requests, not uinput: [virtual-pointer XML](https://github.com/swaywm/wlr-protocols/blob/master/unstable/wlr-virtual-pointer-unstable-v1.xml), [virtual-keyboard XML](https://github.com/swaywm/wlroots/blob/master/protocol/virtual-keyboard-unstable-v1.xml). The latter supports a private keymap/modifier state. This does not prove it can preserve global lock state. Do not use `zwlr_input_inhibit_manager_v1` as a capture fallback: it blocks input to other clients and changes focus, without supplying Openergy's replay/edge semantics. [Input-inhibitor XML](https://github.com/swaywm/wlr-protocols/blob/master/unstable/wlr-input-inhibitor-unstable-v1.xml)

The Clipboard portal extends an existing session: RequestClipboard precedes Start; check `clipboard_enabled`. SelectionRead returns an FD; SelectionTransfer is answered with SelectionWrite and SelectionWriteDone. SelectionOwnerChanged carries MIME/ownership information. This is the selected server-active/client transport, not a generic clipboard permission. [Clipboard portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Clipboard.html)

Direct data-control is a privileged protocol, independent of focus. Use its ownership/offer lifecycle, not a clipboard poller that creates a focused window. [ext-data-control XML](https://github.com/wayland-mirror/wayland-protocols/blob/main/staging/ext-data-control/ext-data-control-v1.xml), [wlr-data-control XML](https://github.com/swaywm/wlr-protocols/blob/master/unstable/wlr-data-control-unstable-v1.xml)

Logical output dimensions include scale and rotation effects; core output modes are not an interchangeable source of desktop coordinates. An integer `wl_output.scale` alone cannot describe fractional desktop scale. Report a fractional scale only where the selected coordinate mapping supplies it; expose unknown precision instead of inventing a physical-pixel ratio. [xdg-output XML](https://github.com/wayland-mirror/wayland-protocols/blob/main/unstable/xdg-output/xdg-output-unstable-v1.xml)

Use the portal Inhibit API for `prevent_sleep`; Wayland idle-inhibit is tied to a visible surface. For systemd sessions, logind provides PrepareForSleep, session active/LockedHint state, and Lock/Unlock signals. Lock/Unlock are requests, so do not treat receipt alone as proof that a lock screen completed. Reconcile state and prioritize compositor session revocation. A non-systemd adapter remains an open compatibility gate. [Inhibit portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Inhibit.html), [idle-inhibit XML](https://github.com/wayland-mirror/wayland-protocols/blob/main/unstable/idle-inhibit/idle-inhibit-unstable-v1.xml), [logind D-Bus API](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html)

## 4. Architecture and required integration changes

### Ownership and transport

Keep source/sink/screens/clipboard proxies in the existing `Backend` slots. Add a Linux-owned session broker thread with one asynchronous runtime. It owns portal proxies, session objects, subscriptions, EI connections and generation counters. A Wayland dispatch worker owns its connection/event queue for registry, outputs and optional direct protocols. Shared snapshots are small and bounded; commands and replies have deadlines. Clipboard FD pumps must not block input dispatch or runtime IPC. A capture worker stop disables delivery without destroying the broker's still-authorized session; explicit authorization reset, role change or daemon shutdown closes it. This prevents health retries from repeatedly creating consent sessions.

Add a `create_wayland_with_notices(options)` constructor at the Linux boundary, analogous to the existing macOS/Windows constructors. The broker's typed Linux notices are mapped by `daemon::adapter` into runtime events. Role/config changes must reach the broker; current construction only passes X11 display options, so this needs explicit integration rather than opening both portal sessions unconditionally.

Client flow: discover RD and device types → explicit authorization → create session/select keyboard+pointer → optional Clipboard request → Start → EI sender connection → bind advertised seat capabilities → wait for devices and regions → publish ready. Do not request ScreenCast by default: Openergy does not share pixels. If a backend cannot expose usable absolute regions without a screen selection, report that gap. Any later ScreenCast opt-in must explain its extra consent and mapping; it is not a hidden prerequisite.

Server flow: discover IC → explicit authorization → v2 CreateSession2/optional Clipboard/Start, or v1 CreateSession with reduced features → EI receiver connection → zones → barriers on linked external edge segments → Enable → compositor Activated → runtime accepts the target → deliver captured input → Release on return. Disabled/Deactivated/Closed are distinct states. Install subscriptions before requests to avoid missing fast responses. Check SetPointerBarriers' failed-barrier IDs; an unaccepted segment must never appear as a usable exit. Rebuild against the latest zone set and never put barriers on internal monitor seams. Ignore stale completion signals by session and activation generation.

### Amend the capture contract instead of faking X11

The current trait is documented as frozen. Changing it needs a reviewed architecture amendment. The proposed amendment has these specific parts:

1. Add capture capabilities distinguishing passive observation, barrier activation, immediate grab, current-event replay, one-event pass, and return-position guarantees. X11 keeps its existing behavior. Add configuration of reachable barrier segments from the **current derived layout**, not a fixed “all monitor edges” rule.
2. Add typed activation/deactivation data at the backend/daemon boundary: session generation, activation ID, zone set, barrier ID and actual activation position. Add a corresponding server-session event for a compositor-initiated edge attempt. Do not encode activation as a fabricated MouseMoveAbs. The session chooses a connected, permitted target using the same layout/ranged links and switch policy as normal movement.
3. Gate input delivery on an explicit runtime acceptance of that activation. The broker holds a bounded input queue while acceptance is pending. Acceptance updates the runtime's remote state and session exit point **before** callbacks see events. Otherwise today's callback sees `remote=false`, returns PassToOs on the first event, and immediately tears capture down. Rejection/timeout releases capture and drops that activation's pending remote events. Queue overflow forces a safe local return; it cannot promise replay of the event already diverted by the compositor.
4. Treat `set_cursor_captured(true)` on IC as acceptance of a live activation, never as an arming request or successful arbitrary grab. `false` releases the current activation. Correlate a subsequent Warp action with that release so its desired position becomes a Release suggestion; do not release first and silently lose the return coordinate. Inactive arbitrary warp returns NotImplemented. Capture/Warp command failures must reach the runtime rather than being discarded by workers.
5. `Swallow` retains active capture. A callback PassToOs releases capture for future physical events; it does not replay the event just received. PassOnce has no equivalent. Never inject a captured event back through RD as generic replay: key state, focus, physical ownership and self-capture can all differ. The existing `capture_overflow` text saying the event passed to the OS must become capability-aware.
6. Replace the assumption that every health refresh has a valid global cursor with an explicit known/unknown/tracked cursor snapshot. This requires a shared API/status amendment because `(i32,i32)` cannot express unknown. The session must not reset its cursor from a guessed `(0,0)` or move a live cursor from a display center. On activation use the real reported position; while remote use session tracking; while local and unknown retain logical history without claiming to query the OS.

There is no generic proof that a key pressed before IC activation will release correctly in the local application. IC does not provide the prior local key stream used by `workers::capture` to implement PassOnce. Modifier masks do not enumerate all held non-modifier keys/buttons. **Server release is blocked until real held-before-crossing flows prove compositor cleanup or a safe deferred-switch policy on each supported stack.** If neither works, that stack is not a supported server. Do not ship the risk as an undocumented sticky-key limitation.

Local lock hotkeys and Scroll Lock are also unobservable while IC is inactive. Initial Wayland server mode must explicitly disable unsupported local lock controls and reject configurations that require them. A future GlobalShortcuts integration could offer an explicitly registered shortcut, but that would be a new UX and would not recover passive observation. Delay/double-tap/required-modifier/dead-corner policy must be evaluated at activation with reliable state. Release rejected attempts without exporting input. If a policy cannot be implemented faithfully, reject that policy for Wayland instead of silently ignoring it.

### Keys, repeat and device state

Retain separate ledgers for source-button identity and owned destination key/button state. Build target symbol lookup from the advertised XKB map with `xkbcommon`; preserve the KeyID/special/media mappings in the existing Linux keymap code where they are independent of X11. Keep X11's global remapping implementation separate. With EI, prefer an available target symbol/level; use negotiated text keysym fallback only when necessary and verified.

Lock synchronization uses known locked masks and bounded EI synchronization outside the per-event callback. Do not toggle from an assumed all-off state. Missing Scroll Lock mapping, unknown modifier state, a paused device or a concurrent local transition must produce a specific failure/degradation. EI does not offer XQueryKeymap for all physical held keys. Separate emulated-device ownership protects releases; it does not prove global physical-state introspection. In particular, a locked-modifier mask cannot prove that the physical lock key is up. Do not claim X11's held-lock-key safety check from that mask. Until the selected compositor path proves safe synchronization, expose lock sync as partial/unsupported and refuse configurations that require exact physical lock parity.

Define repeat behavior at the full path. The source synthesizes `KeyRepeat` only if the capture transport has no equivalent, using the selected seat's repeat settings when available. The sink must account for compositor/application repeat; do not blindly combine a timer with repeated press/release pairs. If explicit repeat pairs are needed, put release and press in separate EI frames. Validate exact counts and no repeats after release/return. Missing reliable repeat settings are reported, not replaced with a claimed native rate.

Device pause/removal, session revocation, lock, peer loss and shutdown stop input routing. Attempt releases on live owned devices, then close invalid sessions and clear only their generation's ledger. A new session never inherits held keys. Accept receiver motion in logical desktop units; do not treat physical-device millimetres as logical pixels. Prefer the compositor's logical/virtual seat device, and reject uncalibrated physical-device motion. Ensure client-side loss triggers `ClientEvent::PermissionLost`; current capture-oriented Notice handling alone does not do this.

### Clipboard data plane

Use the same selected session for input and portal clipboard. Do not open a second RD permission session merely to make server clipboard continuous. Initial portal server support is explicitly **clipboard during active capture**, and only on stacks that grant it. A stricter requirement for continuous sync must fail readiness or require a separately approved direct data-control mode. No replay of stale clipboard data after revoked access.

Map UTF-8 text, HTML, image/png and image/bmp to the existing shared formats. Reuse `image.rs` conversion limits and rejection rules; do not introduce raw PNG on the wire. Read all requested formats against one selection/session generation. Commit the snapshot only if that generation remains current. A change during streaming yields ClipboardUnavailable. A session becoming inactive is not an empty clipboard.

Preserve `max_bytes` across the total converted payload, enforce 64 MiB daemon/image bounds before large allocations, and cap in-flight transfers, FD count and aggregate retained bytes. Proposed initial transfer deadlines and ceilings match X11's existing ten-second transfer timeout, 16 outgoing slots and 256 MiB aggregate safety budget, with the tighter caller/64 MiB limits taking precedence. Use bounded nonblocking FD I/O, handle EPIPE/cancellation, and close all descriptors on timeout/loss. Prove a later transfer still works after an oversized or abandoned transfer.

`write_shared` retains an immutable payload while serving requests. Increment the local stamp once after accepted selection ownership and do not increment it again for that own-write signal. Suppress nonempty own-write reads with ClipboardUnavailable, preserving the explicit-clear exception. Portal owner information/direct source identity provides the loop guard; payload hashes alone cannot distinguish an identical external copy. A read outside allowed session scope fails immediately as unavailable. A write outside scope returns a failure; never report success for data queued indefinitely until some future activation.

### Permissions and user interaction

Construction, status and periodic health checks must not open a permission dialog. Run in the logged-in user's graphical session with its session bus and Wayland socket. A system service, SSH shell with no graphical session, greeter or locked desktop is not an unattended control target.

Proposed policy: explicit `permissions.request` starts authorization; ordinary enabling can restore a prior authorization, but must stop at “needs user action” if fresh consent is required. If the portal cannot guarantee a silent restore attempt, defer Start to that explicit action. Never reissue dialogs in the capture retry loop. First use, rejected/expired restore, role changes that request new capabilities, revocation and some restarts require a person to respond to desktop UI. The person must use the test/session's local input, not a remote connection that has not yet been authorized.

Install a stable app ID/desktop identity. Use an exported parent-window handle if a future native Linux UI provides one; a CLI uses the documented empty parent and explains that the desktop dialog can be unparented. Store distinct IC/RD restore tokens under private per-user daemon state, keyed by app identity/role. Replace consumed tokens atomically; do not put them in shared config, logs, status, or verification artifacts. Persistence is a request, not a promise of login-to-login unattended access.

The existing synchronous `request_permission` cannot wait on a human while the I/O loop serves peers. Schedule authorization on the broker and return `Unknown` while pending; complete via permission/status notices. Keep polling methods side-effect-free. Map InputMonitoring to authorized capture, PostEvents to authorized injection, Accessibility to NotRequired unless a real platform requirement uses it. Mark the unused role's grants NotRequired so a server does not require RD injection consent. “Granted” means the role's required devices are usable, not merely that Start returned success. Unsupported, temporarily missing, pending and denied remain distinct in capability status even though the existing Grant enum cannot express all four.

For direct wlroots mode, disclose that socket/compositor policy replaces portal consent. Bind no raw `/dev/input` or `/dev/uinput`, add no input-group requirement, and request no root/seat-wide exclusive grabs.

## 6. Fallback and status contract

| Detected environment | Client role | Server role | Honest degradation/refusal |
| --- | --- | --- | --- |
| Mutter or KWin with RD/EI keyboard, absolute regions and required pointer capabilities | Candidate full input path after grant; Clipboard separate capability. | Not implied by RD. | Missing repeat/lock/text support is listed independently. No Unicode or global-cursor promise from a successful pointer session. |
| Mutter or KWin with IC, keyboard+pointer and usable barriers | Independent of client. | Candidate edge-triggered mode after capture-contract and held-transition acceptance. | No passive monitoring, arbitrary grab, guaranteed warp, local lock hotkeys, or current-event PassOnce. IC v1 has no new persistence/clipboard negotiation. |
| IC v2 plus Clipboard granted | As supported by RD independently. | Clipboard active during capture. | Continuous clipboard sync unavailable unless separately authorized data-control works. |
| RD present, ConnectToEIS absent | No initial shipping client path. | IC assessed separately. | Optional later D-Bus Notify adapter can inject keysym/keycode and relative input. Absolute Notify uses a ScreenCast stream, so no stream means no normal client Enter. Never mix Notify calls with an established EIS connection. |
| wlroots baseline with virtual-pointer + virtual-keyboard + data-control globals | Optional direct client after explicit opt-in and native acceptance. | Refused without a working IC backend. | Injection/clipboard do not imply capture. Required protocol absent or policy refusal blocks that feature. |
| Any compositor with relative injection but no absolute mapping | Refused for normal client role. | Capture assessed separately. | `input.relative_mouse=true` does not remove the client's absolute Enter requirement. No guessed origin or pretend relative-only success. |
| Wayland desktop with only DISPLAY/XWayland | Not a supported native Wayland path. | Not a supported native Wayland path. | `auto` must not silently choose X11 because DISPLAY exists. Explicit `--platform x11` is a separate X11/XWayland scope with a clear limitation. |
| Portal unavailable, session bus absent, permission cancelled/revoked, seat inactive or required devices removed | Stay unready/stop routing. | Stay local/return local. | Keep status/IPC available. No retry-dialog loop, no privileged-device fallback, no silent virtual backend. |

The D-Bus fallback is deliberately later work. RemoteDesktop documents both Notify methods and EIS, their exclusivity, and stream-scoped absolute coordinates. [RemoteDesktop methods](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html)

Add `--platform wayland`; update help, adapter construction and Linux auto selection. Auto should prefer Wayland for a real graphical Wayland session (session type/socket, not desktop brand), and fail visibly if that selected backend cannot meet the role. Keep explicit x11 and virtual choices. Do not fall back across security models after permission denial. Add Wayland to the native protected-port preflight in `runtime::run`; its current native backend list names macos/x11/windows only.

Proposed config additions, **not current CLI/schema**: `[wayland] transport = "portal" | "direct"` (portal default), `permission_policy = "explicit" | "restore"`, `clipboard_scope = "active" | "continuous"`. Existing clipboard enabled/send/receive settings still apply. Direct means explicitly selected extensions, not an automatic permission bypass. Continuous scope fails feature readiness when only active-session clipboard exists. Reject unsupported server switch/lock policies with actionable validation. Role changes cancel old sessions and request only the new role's rights. Restoring config never serializes consent tokens.

Extend `status.get` additively with backend capability/session data: selected transport, discovered interface versions, required vs granted capabilities, authorization state, `needs_user_action`, session generation, capture armed/active, cursor known/tracked/unknown, geometry freshness/mapping, clipboard scope/formats and reason codes. Never include input content, clipboard bytes, token values, or private bus identifiers. Existing permission fields and `permissions.changed` remain the coarse compatibility view.

Mirror existing runtime reporting, but close its Wayland-specific holes:

- `capture_unavailable` for failed/revoked capture and `injection_failed` for unsupported/unmapped/paused input. Add stable reasons such as `wayland_portal_missing`, `wayland_permission_pending`, `wayland_absolute_unavailable`, `wayland_pass_once_unavailable`, and `wayland_cursor_unknown` under capability details/last_error as appropriate. Cancellation is distinct from an implementation crash.
- `clipboard_failed` and existing unavailable/too-large completion paths remain separate from clear. Publish a capability/scope change even if no clipboard stamp changed.
- On capture loss, reuse the server's local-return/release path. On injection loss, explicitly drive client PermissionLost and release/disconnect. `Notice::Permission` currently only handles an enabled server; it is insufficient by itself for RD revocation.
- `refresh_health` currently treats any Denied grant as failure and treats Unknown as not denied. Add a **role-specific readiness gate** so pending authorization cannot start routing. Keep automatic health retries limited to an already authorized session with no consent action.
- Displays and lifecycle notices wake the same runtime path. Missing notification setup maps to `platform_notifications`; stale screen snapshots remain labeled stale and cannot justify new barriers. A confirmed zero-output layout blocks native input readiness; do not use `display_rect`'s current empty-set 1920×1080 fallback as a real Wayland screen. Ordinary capture deactivation returns local without pretending that permission was permanently denied.

## 7. Phased implementation and end-to-end verification

Follow [CONTRIBUTING.md](../../CONTRIBUTING.md), [Linux lab rules](../../tools/linux-dev/README.md), and the [external runner contract](../../tools/e2e/README.md). Verification uses real processes, compositor connections, daemons, IPC and network peers. Never use the user's active desktop, clipboard, input devices, login service or installed daemon. No computer-use automation. Synthetic input belongs only to a run-owned headless/nested compositor or disposable VM. Human consent/lock acceptance happens on a separate test account/machine with local recovery input.

Do not bypass that gate.

## 8. Human decisions and open risks

1. **Capture API amendment and support promise.** Approve barrier-activated semantics and explicit unknown cursor state, or keep Wayland server unsupported. The present trait's passive observation/PassOnce/immediate-grab contract cannot be promised by generic IC.
2. **Held local input is a release blocker.** Decide whether a verified deferred switch is acceptable if a compositor cannot preserve local key/button releases. There is no proposed silent input reinjection workaround.
3. **Clipboard scope.** Accept active-capture-only server clipboard on portal-only desktops, or require continuous sharing and accept fewer supported stacks. Opening extra consent sessions or direct privileged protocols needs a deliberate product decision.
4. **Local hotkeys and switching rules.** Accept disabling/rejecting unobservable local lock controls initially, or fund a registered-shortcut UX and broader capture-policy work before server release. Decide whether reduced switch policies are acceptable.
5. **Authorization UX and persistence.** Choose the stable app ID, how a CLI user finds/approves unparented dialogs, and whether restore is opt-in or default after first consent. No reliable “never ask again” promise is available across all backends.
6. **Repeat, layout and locks.** Set the minimum reliable semantics for mixed physical/remote keyboards, lock LEDs, international layouts and optional EI text. Missing target symbols must fail visibly. `sync_language` is not generic desktop layout control.
7. **Support floor and CI capacity.** Select and pin actual GNOME/Mutter, Plasma/KWin, portal and libei/reis versions after M1/M2 evidence. Current upstream main and a nominal Rust MSRV do not define the release floor. Fund independent GNOME and KDE acceptance sessions; Weston/Sway alone cannot verify portals.
8. **Rust EI implementation vs native dependency.** Accept reis's current maturity behind an adapter, or choose audited C libei FFI before M2. Keep protocol coverage, distribution packaging, licensing review and ARM64/x86_64 builds explicit.
9. **Lifecycle and multiple seats.** Initial scope is one selected seat in an unlocked logged-in session. Decide whether non-systemd desktops, multiple seats, login screens and unattended service operation are requirements. They need separate designs; they are not implied by this backend.
10. **Geometry compatibility.** Decide the rejection policy for large logical layouts beyond current signed-16-bit wire bounds, inaccessible EI regions, and unknown fractional scale. Refusal is preferable to silent truncation or switching to a location that the compositor cannot address.

The implementation should be announced as a capability-based backend with per-role evidence. The first deliverable is discovery infrastructure; full server support remains conditional on resolving the explicit capture and held-input gaps above.
